## 1. 뭉개기 전 벽 과열도와 뭉갠 후 벽 과열도가 같아야 하나요?

**같습니다. 단, "뭉개기가 ΔT를 보존해서"가 아니라 "뭉개기가 ΔT를 건드리지 않아서"입니다.**

`ΔT_sup = T_wall − T_sat` 인데,

- `T_wall` 은 시뮬레이션의 **입력** (벽 경계조건)
- `T_sat` 은 **유체의 물성** (끓는점)

둘 다 우리가 필드를 어떻게 평균 내든 바뀌지 않습니다. 뭉개기는 **유체 필드**를 평균
내는 작업이고, 벽 경계조건은 손대지 않으니까요.

### 그럼 뭉개기는 뭘 하나 — 실제 숫자 (Twall-90)

| | 미세 격자 | 거친 격자 |
|---|---|---|
| 셀 개수 | 512 | 9 |
| `q″(x)` 범위 | 266 ~ 320 kW/m² (1.2배 변동) | 269 ~ 274 kW/m² (1.0배) |
| **히터 전체 평균** | **272.20 kW/m²** | **272.38 kW/m²** (차이 0.07%) |

즉 **총량은 보존하고, 분포(디테일)는 파괴합니다.** 면적평균이라 열의 총량은 그대로예요.

### 그래서 검증이 성립합니다

1. 정보를 **일부러** 버린다 (거친 CFD가 보는 것을 흉내 냄)
2. 남은 정보(`q″` 숫자 하나)만으로 `ΔT` 를 복원해본다
3. 정답은 우리 처리 과정과 **무관하게** 알고 있으므로 정직한 채점이 된다

정답이 우리 손을 안 탔다는 것 — 이게 BubbleML을 검증 데이터로 쓸 수 있는 이유입니다.

### 한 가지 더: 이건 **최선의 경우 테스트**입니다

우리가 쓰는 거친 `q″` 는 정답 필드를 **완벽하게 면적평균한 값**입니다. 하지만 실제 거친
CFD는 정답 필드를 갖고 있지 않고, 자기 벽 모델로 `q″` 를 **추정**합니다.

> 즉 우리 `q″` 가 실제 CFD의 `q″` 보다 좋습니다.
> **여기서 Cooper가 실패하면, 실제 CFD에서는 확실히 실패합니다.**

발표에서 쓸 수 있는 논리입니다.

## 2. T_wall, T_sat, T_bulk 는 각각 뭔가요?

| 기호 | 이름 | 쉬운 말 | 예 (FC-72) |
|---|---|---|---|
| `T_wall` | 벽 온도 | 히터 표면을 얼마나 뜨겁게 달궜나 | 90 °C |
| `T_sat` | 포화온도 (끓는점) | 그 압력에서 액체가 끓기 시작하는 온도 | 56.6 °C (1기압) |
| `T_bulk` | 벌크 온도 | 히터에서 멀리 떨어진 액체 본체의 온도 | 56.6 °C 또는 그 이하 |

이 셋에서 **두 가지 차이**가 물리적으로 의미가 있습니다:

- **`ΔT_sup = T_wall − T_sat`** ← **벽 과열도**. 우리가 맞히려는 값.
  "끓는점보다 벽이 몇 도 더 뜨거운가". 5도면 살살, 30도면 격렬하게 끓는 중.
- **`ΔT_sub = T_sat − T_bulk`** ← **서브쿨도**. "액체 본체가 끓는점보다 몇 도 차가운가".
  - `0` 이면 **포화 비등** — 액체 전체가 끓는점
  - 양수면 **서브쿨 비등** — 차가운 액체에 뜨거운 히터를 담근 상태

### "정답을 미리 넣어둔다"는 것

맞습니다. 다만 **나중에 쓰려고 저장하는 게 아니라 지금 이 게이트가 바로 씁니다.**

```
T_wall ──┬──▶ (온도 기울기) ──▶ q″ ──▶ Cooper ──▶ 예측 ΔT ──┐
         │                                                   ├──▶ 채점
T_sat ───┴──▶ 정답 ΔT = T_wall − T_sat ────────────────────┘
```

**짚어둘 점**: `T_wall` 이 **두 곳에서** 쓰입니다. 순환 논리는 아닙니다 — 하나는
`T_wall` 과 첫 셀의 차이(기울기)를, 다른 하나는 `T_wall` 과 `T_sat` 의 차이를 쓰니까요.
하지만 **`T_wall` 을 잘못 넣으면 예측과 정답이 둘 다 틀립니다.** 그래서 이 값만은
추측을 금지했고, 코드가 못 찾으면 에러로 멈춥니다.

`T_bulk` 는 왜 필요하냐 → 5번 답을 보세요. 파일의 비율 온도를 실제 온도로 되돌릴 때 씁니다.

## 3. configs 파일로 인풋 설정을 어떻게 했다는 건가요?

**설정 파일 = 코드를 안 고치고 바꿀 수 있는 손잡이 모음**입니다.

코드 안에 숫자를 박아두면 나중에 "이 수가 어디서 나왔지?"에 답을 못 합니다. 그래서
가정이 섞인 값은 전부 밖으로 뺐습니다.

### `configs/default.yaml` — 실데이터용 손잡이

```yaml
data:
  root: data/bubbleml        # HDF5 파일이 있는 폴더
  glob: "*.hdf5"             # 그중 어떤 파일들을 읽을지
  skip_initial_fraction: 0.3 # 앞 30% 프레임은 초기 과도라 버림

nondim:
  temperature_mode: auto     # 온도가 비율인지 실제 온도인지
  length_scale_m: null       # 좌표를 미터로 되돌릴 때 곱할 값
  case_table: {}             # ★ 케이스별 T_wall/T_sat/T_bulk ← 여기에 적습니다

phase:
  phi_positive_in: liquid    # dfun 의 어느 쪽이 액체인지
  mixing_rule: arithmetic    # 섞인 셀에서 k 를 어떻게 섞을지

wall_flux:
  order: 2                   # 온도 기울기를 몇 차로 계산할지
  include_mixed_cells: true  # 섞인 셀을 뺄지 말지 (true = 빼지 않음)

gate:
  mape_max: 0.30             # 통과 기준
  slope_tol: 0.05
```

`case_table` 은 이렇게 채웁니다:

```yaml
  case_table:
    Twall-85: {T_wall_C: 85.0, T_sat_C: 56.6, T_bulk_C: 56.6}
    Twall-90: {T_wall_C: 90.0, T_sat_C: 56.6, T_bulk_C: 56.6}
    Twall-95: {T_wall_C: 95.0, T_sat_C: 56.6, T_bulk_C: 56.6}
```

### `configs/fluids.yaml` — 유체 물성만 따로

```yaml
fluids:
  FC-72:
    T_sat_K: 329.75
    p_operating_Pa: 101325.0
```

### 쓰는 법

```bash
python scripts/run_gate.py --config configs/default.yaml
```

그리고 **실행할 때마다 실제로 어떤 값이 쓰였는지가 `run_manifest.json` 에 기록됩니다.**
나중에 "이 결과는 어떤 가정으로 나온 거지?"에 답할 수 있게요.

## 4. Dirichlet / conjugate 가 무슨 말이고, 어떻게 확인하나요?

### 용어부터

시뮬레이션을 돌리려면 **"벽에서 무슨 일이 일어나는지"를 사람이 정해줘야** 시작됩니다.
방법이 세 가지 있습니다.

| 방법 | 사람이 정해주는 것 | 벽 온도는 |
|---|---|---|
| **벽 온도 못 박기** (Dirichlet) | "이 벽은 90도다. 끝." | **입력**. 정확히 앎 |
| 열유속 못 박기 (Neumann) | "이 벽에서 10만 W/m² 가 나간다" | 솔버가 계산 |
| **고체까지 같이 풀기** (conjugate) | 구리 블록 같은 고체 히터를 도메인에 포함 | 솔버가 계산, **위치·시간마다 다름** |

- **"Dirichlet 경계"** = 값을 못 박는 경계조건. 수학자 이름입니다.
- **"conjugate heat transfer"** = 붙어 있는 **고체와 액체의 열을 동시에** 푸는 것.
  히터가 단순한 표면이 아니라 두께를 가진 물체로 들어갑니다.

### 제가 가정한 것

BubbleML은 **첫 번째**(벽 온도 못 박기)라고 봤습니다. 파일 이름이 `Twall-90` 인 것 자체가
강한 증거예요 — 벽 온도가 실험 조건(=입력)이라는 뜻이니까요. 그래서 90도는 시뮬레이션이
계산한 값이 아니라 **사람이 정해준 값**이고, 그래서 **정확합니다.** 그게 "정답"의 자격입니다.

### 왜 중요한가

세 번째(conjugate)라면 벽 온도가 **하나의 수가 아니라 필드**입니다. 그러면 "정답 ΔT" 하나를
못 정하고 평균을 내야 하는데, **그 평균도 우리의 선택**이 되어버려서 "정답"의 지위를 잃습니다.

### 확인 방법

```bash
python scripts/inspect_bubbleml.py data/bubbleml/Twall-90.hdf5
```

**3번 항목**이 답해줍니다:

- 맨 아래 줄이 **모든 위치·모든 시간에서 똑같은 값** → 그 줄이 곧 벽이고 Dirichlet 확정.
  정답 ΔT 를 데이터에서 바로 읽을 수 있습니다. (가장 좋은 경우)
- 값이 위치마다 다르다면 → 그 줄은 벽이 아니라 **벽에서 반 칸 떨어진 첫 셀**입니다
  (보통 이 경우). 벽 온도는 파일 이름이나 논문에서 가져오면 됩니다.
- 무차원 온도의 **최댓값이 정확히 1.0** 이면 → 비율의 기준이 벽 온도라는 뜻이라 Dirichlet
  방증입니다.

추가 확인: `Twall-85`, `Twall-90`, `Twall-95` 를 나란히 돌려서 **이름의 숫자와 데이터가
일관되게 움직이면** 확정입니다.

## 5. 무차원 온도 환산 규약은 왜 생겼나요? 그냥 Cooper 쓰면 되는 거 아니었나요?

핵심 한 줄: **Cooper 식은 실제 단위를 요구하는데, BubbleML 파일 안의 숫자는 실제 단위가
아닙니다.**

- Cooper가 요구하는 것: `q″` 는 W/m², `ΔT` 는 K (온도 차이)
- BubbleML이 저장한 것: **0~1 사이의 비율**

### 예시

파일에 `0.5` 라고 적혀 있습니다. 0.5도일까요? **아닙니다.**

규약이 `θ = (T − T_bulk) / (T_wall − T_bulk)` 라면, `0.5` 는 **"벌크와 벽의 정확히 중간"**
이라는 뜻입니다. 그러니 `T_bulk = 56.6`, `T_wall = 90` 이면:

```
실제 온도 = 56.6 + 0.5 × (90 − 56.6) = 73.3 °C
```

**즉 Cooper를 쓰기 전에 비율을 실제 온도로 되돌리는 단계가 반드시 필요하고, 되돌리는
공식이 "규약"입니다.** 그 공식이 뭔지 알아야 하고, 제가 그걸 가정했다는 뜻이에요.

여기서 `T_bulk` 가 왜 필요한지도 보입니다 — 되돌리는 공식에 들어가니까요.

### 왜 비율로 저장하나

시뮬레이션 분야의 오래된 관례입니다. 숫자를 0~1 범위로 맞춰 놓으면 (a) 계산이 수치적으로
안정되고, (b) 물리적으로 닮은 조건들을 한 번에 다룰 수 있습니다.

### 틀리면 어떻게 되나

온도 차이가 전부 상수배로 틀림 → `q″` 가 상수배로 틀림 → Cooper 결과가 틀림.
다만 `ΔT` 로 넘어갈 때 세제곱근으로 줄어듭니다 (20% → 약 6%).

## 6. 좌표가 비율로 되어 있어서 확인이 필요하다는 건가요? 어떻게 하나요?

네. **5번과 똑같은 문제인데 이번엔 길이입니다.**

- 파일 안의 `x`, `y` 좌표도 미터가 아니라 비율일 수 있습니다
- 예: `y` 간격이 `0.03` 이라고 적혀 있다 → 0.03 미터? 아닙니다. **"기준 길이의 0.03배"** 입니다
- **기준 길이**가 뭔지 알아야 미터로 되돌립니다

왜 중요하냐: `q″ = k × 온도차 ÷ 거리`. **거리가 2배 틀리면 `q″` 가 2배 틀립니다.**

### 확인 방법 — 나눗셈 한 번이면 끝납니다

1. 파일을 열어 `y` 좌표의 **간격**을 잽니다. 예: `0.03`
2. BubbleML 문서에 "격자 22.7 µm" 라고 적혀 있으니 거꾸로 계산합니다:
   ```
   기준 길이 = 22.7 µm ÷ 0.03 = 757 µm = 0.757 mm
   ```
3. 그 값이 **FC-72 의 모세관 길이(약 0.73 mm)** 와 가까운가?
   - **가깝다** → "기준 길이는 모세관 길이구나" 확정. 설정에 그 값을 적으면 끝
   - **멀다** → 다른 기준이거나 22.7 µm 정보가 틀린 것. par 파일을 찾아야 합니다

제가 쓴 **"역산"** 은 그냥 **거꾸로 계산한다**는 뜻이었습니다. 어려운 말을 썼네요.

### 도구가 자동으로 해줍니다

```bash
python scripts/inspect_bubbleml.py data/bubbleml/Twall-90.hdf5 --expected-grid-um 22.7
```

**4번 항목**이 기준 길이를 역산하고 모세관 길이와 비교해서 답을 찍어줍니다.

> **모세관 길이**란: 유체의 표면장력과 무게가 균형을 이루는 길이입니다. 기포가 자연스럽게
> 갖는 크기의 자 같은 거라, 비등 시뮬레이션에서 길이의 기준자로 흔히 씁니다.

## 7. 물성값들이 BubbleML에서 직접 뽑은 게 아닌가요?

**네, 맞습니다. 제가 교과서/제조사 자료의 FC-72 대표값을 넣었습니다.**

실제 데이터가 없는 상태에서 코드를 돌려보려면 뭔가는 있어야 했거든요. 아무것도 안 넣으면
코드가 아예 안 돌아갑니다.

### 어떤 값이 얼마나 영향을 주나

| 값 | 어디에 영향 | 얼마나 |
|---|---|---|
| `k_l` (액체 열전도도) | `q″` | **1:1 곱셈.** 10% 틀리면 `q″` 10% 틀림 |
| `T_sat` | 정답 ΔT **와** Cooper **둘 다** | 직접 |
| `p_c`, 작동압력 | Cooper 앞 상수 | ΔT 로 감쇠 없이 전달 |
| `k_v` (증기 열전도도) | 섞인 셀의 `q″` | 기포 면적률만큼 |

### 진짜 값 찾는 순서

1. **HDF5 안의 runtime params** — 점검 도구 6번 항목이 있으면 덤프해줍니다
2. **BubbleML 논문**의 물성 표
3. **Flash-X par 파일** — `par` 는 "parameter(설정값)"의 줄임말입니다. 어떤 물성·격자·
   경계조건으로 돌렸는지가 적힌 텍스트 파일이고, 데이터셋과 같이 배포되는 경우가 많습니다
4. 못 찾으면 → 우리가 쓴 값을 "가정"이라고 **명시**하고 민감도를 보여줌

### 좋은 소식

그 값들을 `configs/fluids.yaml` 에 빼놨고 매 실행마다 manifest 에 기록되므로,
**진짜 값을 찾으면 한 줄 고치고 다시 돌리면 끝입니다.** 코드는 안 건드려도 됩니다.
